# Ren'Py release gate — no new candidate while compatibility tests fail

The previous packaged R45 is a historical experiment, not a release approved for testing all classic versions. The previous SDK retry 46109799823 proved both original 32-bit Python 2.3.3 interpreters launch. Ren'Py 4.8.7's old exception logger failed at its own wU open; 5.6.7 returned without a marker. 6.12.2 passed. These observations do not certify 4 or 5.

The new diagnostic driver invokes the exact SDK's native main using the verified bundled interpreter, with the historical 4.x and 5.x initialization interfaces. It preserves actual script parsing, native Text/ Input checks and the result marker; no fake marker or exit-code-only pass. The driver writes the original exception to an absolute path in binary mode. Official source references: https://github.com/renpy/renpy/tree/4.8.7 and https://github.com/renpy/renpy/tree/bcaf88f8a3df9af9308aa4fdee1fd4971c57fd4b (near 5.6.7).

The real build workflow now calls the two required test workflows on the SAME commit. Its build job requires both successes, including the full classic SDK matrix and Windows/Ubuntu and modern SDK matrix. Any failure, cancellation or skip prevents construction, packaging and upload. The previous standalone test workflows remain manually callable. This is a gate for the current representative SDK tests, not certification of all 188 historical releases. The packaged OPUS tests remain required before publication. Do not label an older artifact as a newly approved build.

## Root cause and product correction
Run 46110323917 exposed the native exceptions: both Python 2.3.3 engines failed in codecs.open(..., "rU", "utf-8") when loading their own common scripts, before the translator initialized. CPython 2.3.3 Lib/codecs.py appends b to rU; Objects/fileobject.c recognizes only U/rU, and the old Microsoft CRT can report ENOENT for invalid modes. The production classic startup asset retries only an existing UTF-8 RPY/RPYM read in the native rU mode and preserves the codec wrapper and original bytes. It is invoked through the selected original executable's verified --python entry point, not by replacing any engine. The new Ren'Py-only JUGAR CON IA button and --renpy-play command verify the installation and launch that route for early classic engines; later engines start normally. Native SDK tests exercise the same production compatibility module and compare newline semantics; no original engine is modified. The 4/5 initialization tests are still not full gameplay certification.

## Follow-up: active checks and text eligibility
Run 46110704051 exposed three independent issues: the modern probe had a duplicated tail from a replacement error; Ren'Py 4.8.7's frozen interpreter did not include the ASCII encoding module; and the classic text filter classified closing tags such as {/b} as a path. Restore the intact modern probe with explicit checks, use ASCII-only source without a codec declaration and UTF-8 for ASCII protocol tokens, and inspect markup-free text only for eligibility while preserving the original text submitted to the worker. Unit tests exercise formatted text over the actual classic file transport and compile the outer and embedded Python of both SDK probes. The release gate is unchanged; no packaging until the required matrices pass.

Run 46110964461 confirmed the ASCII and formatted-text fixes: 4.8.7, 6.12.2 and all four modern SDK contracts passed. The remaining 5.6.7 initialization failure occurs in its genuine render.redraw because --lint has not created game.interface. Supply only a fixture frame clock for that version, require the genuine setter to translate the text and append the expected redraw event for the same native object, verify player input, and restore the original interface and queue. This is a headless initialization contract, not a graphical play certification. The production client and release gate are unchanged.
